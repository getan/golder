# 移动端以原生界面接入 Golder 共享 Go 核心

> 状态：产品方向已确认；具体集成和平台能力继续通过实机验证。
>
> 最后更新：2026-11-15
>
> 相关资料：[现有系统架构图](assets/golder-architecture-zh.png)、[桌面 GUI 架构](gui-architecture.md)、[Android 验证备忘](android-coding-agent-memo.md)、[Android 回归测试](android-testing.md)。

## 摘要

Golder 增加原生移动端，而不是为手机重写 Agent。Android 首先使用 Kotlin 原生界面，未来 iPhone 使用 Swift 原生界面；两者通过各自的平台宿主接入同一套 Go Agent 核心。TUI、桌面 GUI 和 CLI 保持原有入口与行为。

首版 Android 尽量在手机本地处理代码和执行受支持的工具，模型推理可以调用远程 API；不依赖电脑在线，也不把“本地执行代码”描述为“本地运行大模型”。移动端默认采用 Golder 的 `auto` 模式，追求任务连续自动化，不为 commit/push 增加 Android 专属的固定人工确认步骤。

本文确定整体方向，不冻结具体桥接协议、支持矩阵或 iOS 实现细节。实验通过不等于正式产品已支持；尚未运行的检查和测试必须如实标注。

## 背景：移动端应成为新的交互入口

现有 [Golder 系统架构图](assets/golder-architecture-zh.png)从原生 GUI、TUI/REPL 和 CLI/Workspace 进入共享 Agent 运行时，再连接模型、工具、会话与权限能力。桌面 GUI 不是 TUI 的终端套壳；移动端也应直接表达任务、消息、工具状态和代码变更，而不是缩放终端界面。

目前已有可复用的基础：

- [`runtime.StartRun`](../internal/runtime/loop.go) 驱动 Agent 循环，[`agentcore`](../internal/agentcore/) 提供消息、事件和工具接口；[`provider`](../internal/provider/) 负责模型协议。
- [`gui/appsession`](../gui/appsession/) 证明了界面可以通过命令、快照和事件使用同一运行时，不必依赖 GUI 控件类型。
- [`session`](../internal/session/) 已有版本化 JSONL 会话和单写者锁；[`permissions`](../internal/permissions/) 和 [`judge`](../internal/judge/) 已有权限与风险决策。
- [`internal/androidagent`](../internal/androidagent/) 是 Android 工具配置实验：它检测搜索与 shell 能力，要求宿主提供授权 gate，但还不是完整移动 App 或生产权限链。

现有组件并非无需适配。例如桌面 [`toolworker`](../internal/toolworker/worker.go) 的默认路径依赖独立工作进程；桌面 controller 也包含浏览器、Computer Use 和终端状态。把桌面入口直接塞进手机并不能保证这些能力可用。

## 设计：原生 UI、移动宿主和共享核心分层

```text
  TUI / CLI        桌面原生 GUI          Android 原生 UI       iOS 原生 UI
  现有入口            MyGo                  Kotlin              Swift（后续）
      │                │                      │                     │
      │                │               Android 宿主 / 桥接     iOS 宿主 / 桥接
      └────────────────┴──────────────────────┴─────────────────────┘
                                      │
                         共享 Go Agent 运行时与服务
                  ┌───────────────────┼───────────────────┐
                  │                   │                   │
             模型 Provider       工具与权限          会话与上下文
```

图表示职责关系，不表示所有前端已使用同一套宿主接口。TUI、桌面 GUI 和 CLI 保持现有实现；移动端先以独立、可测试的宿主适配核心。

### 原生界面负责交互，Agent 核心负责语义

Android 界面使用 Kotlin 原生 UI，优先评估 Jetpack Compose；未来 iOS 使用 Swift 原生 UI，优先评估 SwiftUI。界面负责项目与会话入口、任务输入、流式消息、工具状态、模型选择、diff 和系统交互；不自行实现第二套模型协议、Agent 循环或权限判断。

移动宿主把界面动作转换为核心可理解的命令，并将核心事件和状态快照返回界面。至少需要表达打开工作区、创建或恢复会话、提交任务、取消、切换配置、查看变更以及响应确有必要的用户决策。具体接口形状在原型中验证，不以模拟终端输入作为协议。

### Android 先验证 JNI，iOS 保留独立原生桥接

Android 优先在原生 Kotlin 宿主中验证 JNI 调用 Go 核心。已有实验在测试 App 自身进程通过 JNI 跑通了使用模拟模型的真实 Agent 循环；随 App 安装的 Go 子进程也完成过同类实验。JNI 是当前优先推进的候选，不代表子进程路线已被永久排除，也不代表生产桥接、网络或生命周期已经验证。

iOS 不复用 Android JNI 或 Kotlin UI；它通过适合 Apple 平台的原生桥接调用共享 Go 能力。Go 包的 iOS 目标编译只能作为早期信号，不能证明库链接、签名、设备运行或发布要求已满足。iOS 的桥接、文件访问和后台行为需要单独原型与验收。

跨桥接边界传递结构化命令、事件和快照，而不是暴露 Go 内部对象。宿主需要处理线程切换、有界事件流和界面重建：可合并中间文本增量，但不得把任务结束、工具结果或必要的授权决定悄悄丢失。事件消费中断后应能重新读取一致的状态，而不是靠屏幕文本猜测。

### 生命周期属于宿主，不能承诺系统永不终止任务

移动宿主负责把运行任务与页面生命周期分开：界面重建不应无意重启 Agent；系统允许的后台执行和通知方式按平台版本分别验证。Android 和 iOS 都可能限制后台运行，不能仅因为启动了服务或子进程就承诺任务一定持续。

核心应复用已有 checkpoint 和会话能力，并补足移动场景的中断验证。恢复时区分已完成、失败、已取消和结果未知。对于可能已经产生的文件、Git 或网络写入，结果未知时先检查实际状态，不自动重放；checkpoint 本身不构成远端操作“恰好一次”的保证。

## Android MVP：先让手机独立完成一部分真实任务

### 工作区先由 App 管理

首版以 App 管理的私有工作区为主，支持将仓库 clone 到手机，并提供导入、导出或备份路径；暂不承诺直接原地编辑任意共享目录。系统文件选择器返回的对象不一定是普通文件系统路径，不能未经适配就交给现有 Go 文件工具。

App 卸载通常会删除其内部私有数据。界面和导出流程必须让用户理解并控制这一风险，不能把唯一副本悄悄留在会随卸载删除的目录中。

### 文件与搜索优先复用现有能力

读取、列目录、补丁和 diff 优先复用 Golder 的文件能力；真实代码变更应能查看 diff，并提供实际可用的撤销或恢复方式，不将文件回滚表述为可以撤销任意外部副作用。

搜索按设备实际能力提供：有可用的 `rg` 时可使用现有专用搜索工具；没有 `rg` 时可使用 Android 系统 `grep` / `find` 的已验证路径，并诚实说明参数、正则及忽略规则可能不同。如果替代命令不可用或当前权限不允许执行，不应暴露必然失败的能力，也不应声称搜索成功。

Android 常规工作区操作应尽量自动完成。当前实验原型中的 shell 没有工作区级 OS 沙箱：其工作目录不是权限边界，命令可能访问同一 App 有权访问的工作区外数据；逐命令断网也尚未提供。宿主必须按实际能力和现有 gate 决策并如实表达限制，不能因用户选择了 `auto` 就假装隔离存在。

### Git 作为移动端能力接入，而不是假设系统有 `git`

优先继续评估 Go Git 库路线。实验已在 App 身份下验证部分本地操作，并以开启 CGO 的 Go 探针、默认 DNS 和正常 TLS 校验完成公开 HTTPS clone。它还没有接入 Golder 正式工具集；私有仓库认证、真实 push、子模块和更广泛的 Git 兼容性都未通过验证。

Git 库不等于提供了一个可供 shell 直接运行的 `git` 命令。移动宿主需要向 Agent 提供明确、受权限决策约束的 Git 能力；不能静默声称支持所有桌面 Git 命令、hooks 或辅助程序。实验中默认 `file://` 传输因缺少系统 Git 辅助程序失败，嵌入式测试服务的成功不能当成默认传输已可用。

Android 网络原型中，关闭 CGO 的 Go DNS 曾失败；开启 CGO 后，App 身份的子进程用系统解析器成功完成公开 HTTPS clone。Android 构建可据此优先验证 CGO 和 NDK 路线，但不写死 IP、不关闭 TLS 验证，也不把单台设备的结果推广为所有网络和 JNI 场景已通过。

## 权限与数据：默认自动，不虚构隔离

移动端默认使用 Golder `auto` 模式。宿主根据用户任务意图、具体操作和已获授权能力接入既有决策机制，尽量让常规工作连续完成；缺少身份、授权或必须由用户决定的条件时才请求用户，不重复询问同一决定。

commit/push 在默认 `auto` 模式下按任务意图和现有权限决策自动执行，**不因 Android 额外固定一次人工确认**。执行必须绑定正确的仓库和目标；执行结果未知时检查实际状态，不盲目重放。

不能直接把公开 Go SDK 的默认行为等同于上述 `auto`：当前 [`agent.Session`](../agent/doc.go) 默认工具可自动执行，移动宿主仍需明确接入所需的权限链、平台能力和用户状态。现有 Android 工具原型要求宿主注入 gate；测试中的固定授权桩不是生产审核实现。

模型密钥和 Git 凭据应由移动平台的安全存储机制管理，例如 Android Keystore 保护的存储和 iOS Keychain；核心只在需要时获得相应凭据，不能把密钥写进事件、日志或仓库地址。具体存储、迁移和认证流程需要分别验证，App 级沙箱也不等于同一 App 内的任意 shell 无法触及所有敏感能力。

## 理由与取舍

### 为什么不做一套独立的移动 Agent？

复用现有 Go 循环、Provider、工具语义、会话和权限决策，能避免 Android、iOS 与桌面在模型行为和故障处理上各自分叉。代价是必须建立清晰的平台能力边界，并逐项排除桌面进程、终端和窗口假设。

### 为什么不直接使用桌面 GUI 或 TUI 作为手机后端？

桌面 GUI controller 的快照、事件和命令模式可借鉴，但其当前实现包含桌面浏览器、Computer Use、终端和 controller 关闭时取消运行等行为。TUI 字符屏幕也不是稳定的移动业务协议。我们先复用核心和语义，只有在边界确实通用时才逐步提取共享代码。

### 为什么先以 App 私有工作区为主？

它与已验证的文件和 Git 原型更接近，也能让第一版明确支持范围；代价是需要认真解决导入、导出和卸载数据丢失。直接编辑任意系统文件提供了不同的体验，但其权限和文件系统语义不能先假定与本地路径一致。

### 为什么不先做完整 Linux 沙箱或 Linux 环境？

第一阶段不依赖 Termux、Docker 或任意 Linux 二进制。Android 自带 App 级隔离足以作为早期原型基础，但不等于拥有工作区级 shell 沙箱；我们必须对这一差异保持诚实，并在实现权限与命令边界时实测，而不是为了减少交互放宽未经授权的能力。

## 兼容性与交付

移动端以增量方式接入。现有 macOS、Linux、Windows 的 TUI、GUI、CLI、默认工具选择和权限行为不因移动端默认改变。确需修改共享代码时，先建立平台边界和回归测试；不要求桌面前端迁移到新的移动宿主，也不提前决定 iOS 具体桥接。

建议按以下顺序交付，每一步都可依据结果调整：

1. **移动核心边界**：明确最小会话、事件、取消和宿主授权入口，复用真实 Go 循环，先用模拟模型验证。
2. **Android 原生界面骨架**：接入项目、任务、流式消息、工具状态和 diff；不依赖手机上的桌面 TUI。
3. **真实工作区闭环**：验证真实模型 API、文件搜索和修改，并接入生产 `auto` 决策链。
4. **Git 和数据流转**：先完善本地操作与公开 clone，再验证凭据、私有仓库和 push；实现导入、导出或备份。
5. **生命周期与兼容性**：实测锁屏、后台、系统终止、网络变化、存储不足和结果未知的恢复；保持桌面回归测试。
6. **iOS 可行性原型**：在 Android 基础能力和共享边界明确后，用原生 Swift 界面验证桥接、存储和生命周期，再决定具体交付范围。

## 尚待验证的问题

- JNI 与 Android 子进程在真实流式任务、取消、崩溃隔离、内存和更多设备上的表现，是否足以确定最终集成方式？
- Android 系统搜索、Go Git 及后续打包工具的功能边界是什么；不支持的选项如何明确报告？
- 移动宿主如何接入生产 `auto` 权限链，以及如何处理没有工作区级 shell 或逐命令网络隔离的情况？
- App 进程被系统终止后，哪些任务可恢复、哪些结果只能标记为未知？
- iOS 原生桥接、文件访问、后台能力和平台发布要求是否满足产品目标？

这些问题通过后续实验和评审逐项收敛；本文不把它们视为已经实现的能力。
