# Android 原生 Coding Agent 备忘

本文记录产品方向与当前验证进度，不是已确定的技术方案。后续按实际测试结果逐步决定支持范围和实现方式。

## 产品方向

- 面向手机重新设计任务、代码变更、权限决策和结果查看体验，而不是简单缩放桌面 CLI。
- 尽量在手机本地保存和处理代码、执行受支持的工具；模型推理初期可以调用远程 API。**本地执行代码不等于本地运行大模型。**
- 第一阶段不依赖 Termux，不以手机 GUI 操控或 Computer Use 为目标，也不承诺兼容全部 Linux 软件、Docker 或任意项目测试。
- 候选 MVP 包括打开或 clone 仓库、读取和搜索代码、修改文件、查看 diff，以及按任务意图执行 commit/push。设备实际支持的检查和测试逐项验证；未运行的测试必须明确标注“未运行”。
- 默认采用与 Golder 一致的 `auto` 模式，追求任务的连续自动化：根据具体任务意图、操作风险和已获授权能力自动决策，尽量不打断用户；不能因模型请求本身而假定它已有权限。仅在需要身份、授权或人工决策等实际条件时请求用户，避免重复确认。
- 在已选工作区内自动完成常规读取和搜索；按任务修改代码时展示 diff，并提供可用的撤销或恢复能力。默认 `auto` 模式下，commit/push 按任务意图和与 macOS 一致的权限决策自动执行，不额外要求人工确认；仍须绑定正确目标，缺少必要身份或授权时才请求用户，执行结果未知时不得自动重放。
- 优先利用 Android 自带的 App 级隔离，不要求第一版移植完整桌面沙箱。搜索优先考虑受控调用系统工具；任意 shell 若提供，按实际风险和授权能力决策并如实说明权限边界，不能把工作目录当成安全沙箱。具体权限和隔离方式仍待实现与验证。
- App 私有目录可以作为工作区候选，但用户代码不能只依赖该目录：卸载 App 通常会删除私有数据，需要考虑导入、导出或同步。
- 后台或进程意外终止后，应区分成功、失败和结果未知；尤其不能盲目重放可能已执行的写操作。

## 已验证的信号

以下是 Android 14、ARM64 环境下的有限实机探索结果，不代表所有机型或正式 App 均已支持：

- Golder 的 `agentcore` 消息序列化探针可在 Android 上运行。隔离 Android 不需要的 Linux 桌面 Computer Use 实现后，真实 `runtime` 可针对 Android ARM64、关闭 CGO 交叉编译。
- ADB shell 中，真实 Agent 循环跑通了模拟模型、本地测试工具和结果回传。
- 测试 App 在自身私有目录中完成了文件写入、同步、重命名、读取和删除。
- 独立 Go Git 库候选在测试 App 私有目录中完成了本地仓库创建、暂存、提交、状态和提交间 diff；使用嵌入式测试服务的本地文件仓库完成了 clone、fetch 和 push。默认 `file://` 传输曾因系统缺少 Git 辅助程序失败，测试服务仅用于隔离验证，不能当作默认传输已可用。
- 关闭 CGO 的 Go DNS 探针此前在 Android ADB shell 中解析失败。随后在测试 App 身份的子进程中，开启 CGO 的 Go Git 探针使用默认解析方式成功以 HTTPS 域名 clone 公开仓库；Go 诊断日志显示使用了 cgo 解析器。测试没有写死 IP、关闭 TLS 验证、使用用户凭据或进行公网 push。JNI 进程内网络、真实 App 集成、认证和远端写入仍待验证。
- 同一测试 App 中，通过随安装包提供的 Android ARM64 程序启动了真实 Agent 循环；另一个原型通过 JNI 在 App 自身进程中完成了同类模拟工具回合。两者均为可行性实验，尚未决定正式集成方式。
- 在 JNI 测试原型的私有样例工作区中，真实 Agent 循环调度 `read`、`apply_patch` 并读回修改成功，补丁返回了 diff，工作区外读取被拒绝。模型是模拟的，未验证正式 App 的审批流程。
- 当前专用 `grep` 和 `find` 工具依赖外部 ripgrep；测试 App 环境中没有 `rg`。Android 专用工具配置原型会根据发现的能力选择搜索工具及对应提示，并使用系统 shell；在 App 身份的子进程和私有样例工作区内，模拟模型完成了读取、系统 `grep`/`find` 搜索、修改及读回。测试使用仅允许固定样例调用的授权桩，不代表生产自动审核已完成。
- 上述 shell 实验没有配置生产沙箱或审批链，仅设置工作目录并不能阻止命令读取同一 App 私有空间中工作区外的文件。原型要求宿主提供授权 gate；默认 `auto` 模式下，未获宿主单次授权且没有可用 runner 时拒绝执行。原型不提供逐命令网络隔离，不能强制断网；显式要求 `network=off` 会被拒绝而不是假装生效。正式开放命令前仍需验证工作区隔离、授权和失败处理。
- 从 App 私有**可写**目录直接启动复制进去的可执行文件时，测试设备返回权限错误；因此不能假定下载工具后直接执行的桌面工作流可用。随包执行的实验结果也不能直接推广到所有设备或发布渠道。

## 后续逐项验证

1. 继续验证真实文件工具、代码搜索与 diff 在 App 工作区内的行为与权限边界，接入正式宿主权限链并验证更复杂的工作区场景。
2. 验证远程模型 API、流式事件和取消；明确网络访问与用户凭据的管理方式。
3. 验证 Git clone、commit、push 及认证方式，明确哪些能力可以内置、哪些需要随 App 提供兼容组件。
4. 选择少量有代表性的检查或测试工具实测；对不支持的语言、依赖和测试如实报告。
5. 实测锁屏、切后台、系统终止与重启后的状态恢复，并核查不确定结果下的写操作安全性。
6. 比较 JNI 与子进程在通信、取消、崩溃隔离、资源消耗及多设备兼容性上的实际表现，再决定是否收敛为一种路线。

具体技术选型和支持矩阵以这些验证结果为准，不以本备忘视为已承诺功能。
