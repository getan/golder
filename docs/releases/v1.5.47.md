# v1.5.47 — Double-clickable GUI packages

`golder-gui` can now be installed the way a desktop app is: drag it to
Applications, run an installer, or use a system package. Nothing about the CLI
or TUI changes.

## Artifacts

| Platform | Output | How a person opens it |
|---|---|---|
| macOS | `Golder GUI.app`, `golder-gui-<version>-<arch>.dmg` | mount the DMG, drag to Applications, double-click |
| Windows | `Golder GUI.exe`, `golder-gui-setup-<version>-amd64.exe` | run the installer, then the Start-menu shortcut |
| Linux | `golder-gui`, `.desktop`, `golder-gui-<version>-linux-<arch>.tar.gz` (with `install.sh`), `.deb`, `PKGBUILD` | `install.sh`, `apt install ./…deb`, or `makepkg -si` |

The app is named **Golder GUI** with the slug `golder-gui`, so its Linux
executable never collides with the `golder` CLI.

## The CLI travels with the app

A window that opens a terminal workspace runs `golder workspace attach`. A
packaged app must not depend on the person's `PATH`, so the workflow compiles
the CLI into the bundle:

```text
Golder GUI.app/Contents/Resources/bin/golder
```

Resolution order is: app resources, `GOLDER_BIN`, the executable's directory,
then `PATH`. For the universal macOS app the resource is a universal binary made
with `lipo`.

## How the release is ordered

On a tag, `gui` and `release` start together. goreleaser owns the GitHub
Release, so the GUI job only uploads artifacts; a separate `gui-attach`
workflow waits for `gui` to finish and then attaches the packages to the release
that goreleaser created. This avoids the "release already exists" race without
duplicating the build.

## Signing

Ad-hoc signing is the default, and it is enough to run the app on the machine
that built it. Another Mac refuses it until either:

- the person right-clicks → Open once, or clears the quarantine bit:
  `xattr -d com.apple.quarantine "/Applications/Golder GUI.app"`; or
- the repository has `MACOS_SIGNING_IDENTITY`, `MACOS_CERT_P12`,
  `MACOS_CERT_PASSWORD`, `APPLE_ID`, `APPLE_APP_PASSWORD` and `APPLE_TEAM_ID`,
  in which case the workflow imports the certificate, creates the
  `golder-notary` keychain profile that `gui/mygo.json` names, and `mygo build`
  signs, notarizes and staples.

## Also in this release

- `docs/lark-mcp-setup.md`: the Lark MCP runbook, written for an agent on a
  fresh machine. It records why pnpm 10+ must allow the `@larksuite/cli` build
  script (the native binary lands there), how to find and pin the payloads, and
  that authorization goes through `golder mcp setup`, not the binary directly.
- Documentation and test fixtures no longer contain the author's home
  directory or external volume name; `/srv/...` and `/Volumes/External` stand
  in. Earlier commits still contain the originals, which is a separate
  history-rewrite decision.

## Known limits

- The GUI has no embedded tuios workspace: it opens
  `golder workspace attach` in a terminal window.
- Browser previews are read-only PNGs from the control socket.
- Windows installers are produced by MyGo with NSIS; build them on a Windows
  runner.
