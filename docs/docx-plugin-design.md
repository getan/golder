# docx 插件安全审计与设计

> 实现状态：已完成，代码在 `extension/plugins/docx/`。工具为 `docx_read`、
> `docx_create`、`docx_edit`，覆盖标题、段落、列表、表格、图片、占位符替换与
> 追加内容。依赖固定为 `github.com/mmonterroca/docxgo/v2 v2.16.0`。读取路径直接
> 解析 `word/document.xml`，因为该版本 docxgo 的 `Paragraph.Style()` 始终返回
> nil，无法可靠识别标题；写入仍使用 docxgo。使用说明见插件 README。

## 1. 审计对象

- 仓库：`https://github.com/mmonterroca/docxgo`
- 审计 commit：`fbd073b`（Merge pull request #133）
- 模块：`github.com/mmonterroca/docxgo/v2`，`go 1.23`
- 许可证：MIT
- 规模：约 3.7 MB、238 个文件
- 验证结果：
  - `go list -m all`：只有自身 module，无第三方 Go 依赖
  - `go test ./...`：通过
  - `go test -race ./...`：通过
  - `go vet ./...`：通过

结论：这是一个可用的 docx 读写库，供应链面很小，但**不是为处理不可信文档设计的**。直接把它暴露给模型处理任意 docx 会有明确的资源耗尽、宏/嵌入内容保留和输出路径风险。插件必须在外层加安全封装，而不是把库当安全边界。

## 2. 审计发现

| 级别 | 发现 | 证据 | 影响 |
|---|---|---|---|
| 高 | ZIP 解压无资源上限 | `internal/reader/reader.go` 的 `LoadPackageFromStream` 用 `io.ReadAll` 读整个输入；`readZipFile` 对每个 entry 用 `io.ReadAll`；无 entry 数、单 entry、总解压大小或压缩比限制 | 恶意 docx 可造成内存耗尽/进程 OOM；golder 主进程若同进程加载会被拖垮 |
| 高 | XML 解析无深度/大小上限 | `internal/reader/element.go` 递归 `parseElement`；`xml.NewDecoder` 无深度限制；XML part 大小无上限 | 深层嵌套或超大 XML 可造成栈/堆耗尽。Go 标准库不解析外部实体，未发现 XXE 网络读取，但拒绝服务仍成立 |
| 中高 | 宏/嵌入/未知 part 会被保留 | `internal/reader/package.go` 的 `AdditionalParts` 注释明确为“captures any payload we do not process yet”；reader 把未知 part 复制进 `AdditionalParts`；writer 会原样写回 | `.docm`、`vbaProject.bin`、嵌入 OLE、altChunk 等可能被带入输出；库不执行宏，但生成的文档可能在 Word 中触发/携带活动内容 |
| 中 | 保存不是原子写，且跟随 symlink | `internal/core/document.go` 的 `SaveAs` 直接 `os.Create(path)` | 失败会截断已有文件；目标 symlink 可把写入引到工作区外 |
| 中 | ZIP entry 名称未经安全清洗 | `internal/writer/zip.go` 的 `writeRaw` 直接把传入路径交给 `zip.Writer.Create` | 库本身不解压，但把不可信 part 名写进输出；下游若直接解压会有路径风险 |
| 中 | CLI/JSON-RPC 接受任意文件路径和无限 stdin | `cmd/docxgo/handlers.go` 的 `document.open`/`document.save`；`cmd/docxgo/exec.go` 的 `io.ReadAll(os.Stdin)` | 如果插件通过 CLI 调用，等于把任意路径读写和输入大小暴露给模型；不建议这样集成 |
| 中低 | 图片读取无字节/像素上限 | `ReadImageFromReader` 用 `io.ReadAll`；`getImageDimensions` 只用 `image.DecodeConfig`（好），但没有尺寸/像素上限 | 大图或大量图片可造成内存/输出膨胀；`DecodeConfig` 不会完整解码像素，图像 bomb 风险低于完整 decode，但仍需限制 |
| 低 | 外部关系仅作为数据保留 | 未发现 `net/http` 主动请求；`TargetMode="External"` 只出现在 rels 数据中 | 不会自动 SSRF；但输出中的外链需要 scheme 白名单，文档文本也不能被当作指令 |
| 信息 | 无第三方 Go 依赖 | `go.mod` 只有 module 声明 | 供应链攻击面小；npm 包和 C# validator 不是 Go 运行时，插件不应打包/调用它们 |

### 不该直接依赖的部分

- 不要调用 `cmd/docxgo` 的 JSON-RPC/CLI 作为插件后端。
- 不要对不可信 docx 做“原样 round-trip 保存”；那会保留宏、嵌入对象和未知 part。
- 不要把库的 `SaveAs` 直接暴露给模型路径。
- 不要同进程加载不受限的 docx；插件应是独立进程，失败不能拖垮 golder。

## 3. 插件定位

采用 golder 当前的 **MCP stdio 扩展**形态，而不是 legacy `extension/plugin` RPC：

- 可执行文件：`golder-docx`
- 目录：`extension/plugins/docx/`
  - `cmd/golder-docx/`：MCP 入口
  - `internal/docxmcp/`：工具、schema、审计、路径和限制
  - `skills/docx/`：使用说明（数据，不自动执行）
  - `NOTICE`/`CREDITS.md`：docxgo MIT 归属
- 进程由 golder 的 MCP host 启动，继承项目 cwd，使用 scrubbed env 和 OS sandbox；配置 `network=false`。
- 插件仍自己做路径/大小/格式校验，不把 host sandbox 当成唯一防线。

配置示例（默认 disabled，需显式批准）：

```toml
[mcp.servers.docx]
enabled = false
transport = "stdio"
command = "/abs/path/golder-docx"
args = ["serve"]
allowed_tools = ["docx_read", "docx_create", "docx_edit"]
call_timeout = "30s"
network = false
```

## 4. 工具 API（MVP）

只暴露“文档语义”，不暴露原始 OOXML/XML 编辑。

### `docx_read`（只读）

```json
{
  "path": "docs/report.docx",
  "format": "text",
  "max_chars": 200000
}
```

- `format`: `text` | `markdown` | `outline`
- 返回段落/标题/表格的结构化摘要或文本；不执行宏、不解析外链、不下载图片。
- 输出标记为 untrusted document content；控制字符过滤。

### `docx_create`（写，destructive hint）

```json
{
  "path": "docs/report.docx",
  "title": "Quarterly report",
  "blocks": [
    {"type": "heading", "level": 1, "text": "Summary"},
    {"type": "paragraph", "text": "..."},
    {"type": "bullets", "items": ["..."]},
    {"type": "table", "rows": [["a", "b"], ["1", "2"]]}
  ],
  "overwrite": false
}
```

- 只生成新的规范 docx，不复制输入 part。
- 第一版不支持图片、宏、外链和原始 XML；图片在 Phase 3 单独加限制。
- 输出失败必须报告“未知/未执行”，不能把半成品说成成功。

### `docx_edit`（写，destructive hint）

```json
{
  "path": "docs/template.docx",
  "output": "docs/filled.docx",
  "replacements": {"{{name}}": "Alice"},
  "append": [
    {"type": "paragraph", "text": "Generated by golder"}
  ]
}
```

- 第一版只做文本替换和追加段落/标题/表格。
- 模板必须是工作区内的 `.docx`，拒绝 `.docm`、加密包、OLE 包、宏 part 和不可信嵌入对象。

## 5. 安全处理管线

### 5.1 输入路径

- 根目录来自插件进程 cwd；启动时确认 `os.Getwd()` 非空。
- 只接受工作区相对路径；拒绝绝对路径、`..`、NUL、反斜杠逃逸。
- `Lstat` 必须是普通文件；拒绝 symlink；`EvalSymlinks` 后必须仍在 root 下。
- 只允许 `.docx`；读文件时一次性读入并限制大小，避免校验后文件被替换。

### 5.2 包级预检（在调用 docxgo 前）

- 用 `archive/zip` 读取 central directory。
- 拒绝加密 entry、目录 entry 之外的 symlink、未知压缩方法。
- 限制 entry 数量、单 entry 解压大小、总解压大小和压缩比。
- 拒绝绝对/`..`/反斜杠/NUL/Case-fold 重复的 part 名。
- 拒绝 `EncryptedPackage`、OLE 复合文件头、`.docm`、`vbaProject.bin`、`word/vbaData.xml`。
- 拒绝 `altChunk`、OLE/嵌入对象和宏启用 content type。
- 只允许 `.docx` 主 content type；宏启用主类型直接失败。

建议上限（可配置，但不可由模型调大）：

| 项 | 上限 |
|---|---|
| 输入 docx | 25 MiB |
| ZIP entries | 1024 |
| 单 entry 解压 | 32 MiB |
| 总解压 | 128 MiB |
| 压缩比 | 200:1（总大小仍受 128 MiB 限制） |
| XML part | 32 MiB |
| XML 深度 | 128 |
| 图片单文件 | 20 MiB |
| 图片总像素/张数 | 25M pixels / 64 张 |
| 读取文本输出 | 2M chars |
| 输出 docx | 50 MiB |
| 单次处理超时 | 30s |

### 5.3 解析与输出

- 读路径使用 docxgo 的 reader，但先完成上面的预检；解析失败返回稳定错误码。
- 写路径永远从模型的结构化输入新建 docx，不做不可信原包 round-trip。
- 图片（Phase 3）：只允许 PNG/JPEG/GIF；用 `image.Decode` 完整解码后重新编码，剥离元数据，限制像素；不允许 SVG/WEBP/TIFF。
- 外链：不自动请求；生成文档时只允许 `https`/`http`/`mailto`，拒绝 `file:`、`javascript:`、UNC、data URI。
- 文档文本属于 untrusted content：工具输出要包裹/标注，模型不得执行文档里的“指令”。

### 5.4 输出路径与原子写

- 只接受工作区相对 `.docx` 路径；父目录必须已存在且在 root 下。
- 目标存在时默认拒绝；`overwrite=true` 才允许。
- 目标/父目录做 `Lstat`，拒绝 symlink。
- 在目标目录创建 `CreateTemp`（0600），写完 `Sync`、关闭、`Rename`；失败删除临时文件。
- 错误信息只给路径/类别，不回显文档正文或凭据。

### 5.5 进程与资源隔离

- MCP host：`network=false`、scrubbed env、OS sandbox、`call_timeout`。
- 插件作为独立进程；出现 panic/OOM 只影响该工具调用，不让 golder 主进程崩溃。
- 插件内设置软内存上限（例如 `debug.SetMemoryLimit(512 MiB)`）并检查 `ctx`；这只是纵深防御，不能替代预检。
- 所有循环/递归处理都有上限；XML 预检拒绝过深结构。

## 6. 威胁模型

| 威胁 | 控制 |
|---|---|
| ZIP bomb / 超大 XML | 预检 + 大小/深度/entry 上限 + 独立进程 + 超时 |
| 宏/嵌入对象/altChunk | 拒绝宏启用包；不原样 round-trip；只从结构化模型新建 |
| 路径穿越/绝对路径/symlink | 相对路径 + `EvalSymlinks` + `Lstat` + root 检查 + 原子写 |
| 覆盖已有文件 | 默认拒绝；显式 `overwrite`；原子 rename |
| 外链 SSRF/隐私 | 不自动请求；scheme 白名单；`network=false` |
| 文档内容 prompt injection | 输出标记为不可信数据；不执行文档内指令；控制字符过滤 |
| 图片 bomb/polyglot | 完整 decode + 重编码 + 像素/格式限制 |
| CLI/RPC 任意路径 | 插件直接 import library，不调用 `cmd/docxgo` |
| 依赖/供应链 | 无第三方 Go 依赖；固定审计 commit/版本；MIT NOTICE；不打包 npm/C# |
| 插件崩溃拖垮 host | 独立进程；host sandbox 与 timeout |

## 7. 实施计划

### Phase 0：骨架与供应链

- 在 `extension/plugins/docx` 建 MCP stdio 二进制。
- 固定 docxgo 依赖到已审计 commit/版本；加 MIT NOTICE/CREDITS。
- 接入 MCP `initialize`、工具 listing、`call_timeout`、`network=false`。

### Phase 1：只读安全读取

- `docx_read`（text/outline）。
- 包预检、路径检查、大小/深度/entry 限制、错误码。
- 恶意 corpus：zip bomb、深 XML、宏包、加密包、`.docm`、symlink、路径穿越、超大图片。

### Phase 2：新建文档

- `docx_create`：标题、段落、列表、表格。
- 原子写、覆盖保护、输出上限。
- golden 测试：生成后重新读取结构一致；LibreOffice headless（可选）验证可打开。

### Phase 3：编辑/模板与图片

- `docx_edit`：占位符替换、追加 blocks。
- 图片：完整 decode/重编码、像素上限；拒绝 SVG/WEBP/TIFF。
- 模板只允许工作区可信文件；宏/嵌入对象拒绝。

### Phase 4：golder 集成

- `/mcp inspect docx`、显式 enable、source trust。
- `skills/docx/SKILL.md` 使用说明。
- 工具描述标注 read-only/destructive hints；写操作走宿主审批。

## 8. 验收标准

- 任何输入都不能让插件写 root 外、跟随 symlink、覆盖未授权文件。
- zip/XML/图片攻击均 fail closed，返回稳定错误码；host 进程保持存活。
- 生成的 `.docx` 只包含规范 part，无宏、嵌入对象、altChunk 和外链副作用。
- `docx_read` 不发起网络请求；文档文本被标记为不可信数据。
- 恶意 corpus、fuzz、`go test -race ./...` 和 `go vet ./...` 通过。
- 在 golder 中默认 disabled；显式 enable 后才能发现/调用；写工具需要审批。

## 9. 待确认

2. MVP 是否需要图片；建议 Phase 3 再加，先保证文本/表格安全。
3. 是否需要读取 `.docm` 的文本（仍不执行宏）；建议默认拒绝，避免让用户误以为安全。
4. 插件根目录是否始终等于 host cwd；若某些启动路径不保证，增加强制 `--root` 配置并纳入 source fingerprint。
